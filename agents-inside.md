# Agents inside zenonum

These roles serve the founder’s venture. Twenty-four product agents is the operating count, plus deterministic engines that are deliberately not agents.

The founder meets one voice. The others work on the graph, on a schedule, or behind administration.

## Voices the founder can hear

| Role | Mandate | Forbidden |
| --- | --- | --- |
| Discovery coach | Carry the first conversation, before the map is open | Pretend the workspace is already a live plan |
| Coach | Clarify, teach a method term, acknowledge a fact, ask one next question | Write the canonical graph. Show machine fields. Do the extractor’s job |
| Guardrail | Refuse input that is unsafe, off-policy, or absurdly large, on a stated cadence | Become a second coach. Skip itself for a normal founder |
| Research agent | After a confirmed brief, gather external material and file a report | Search the web because a sentence sounded interesting |

The coach is proactive. It is not a registrar that only stores what it was told. It also does not quietly become the extractor. Those are different mandates, and merging them produced drafts the founder could not see.

## Writers and judges on the graph

| Role | Mandate | Forbidden |
| --- | --- | --- |
| Extractor | Propose canonical nodes, relations, and variables from the conversation | Speak to the founder. Run a second time at save to “improve” the preview |
| Local critic | Reject a draft, or a proposed child, that does not hold together locally | Overwrite a founder decision. Show its private reason |
| Contradiction sweep | On a changed graph, find tensions worth a contradiction node | Delete nodes to make the tension disappear |
| Required-move judge | Name the gap the method still requires | Replace the founder’s priority with its own strategy |
| Acceptance-child proposer | After a goal becomes canonical, propose the children that goal implies | Invent children on every save |
| Prerequisite scaffolder | Propose the chain from the current node toward the far target | Run during an ordinary send |
| Variable estimator | Estimate variables the conversation left open | Present an estimate as a measurement |
| Graph builder | After save, and on a daily whole-plan pass, propose structure the map is missing | Bypass save. Run as a second extractor |
| Existential-risk voice | On a slow clock, when the graph changed, narrate the way this plan dies | Fire on every message. Block the coach |
| Output repair | When a model returns a shape the schema cannot accept, repair the shape | Invent new business facts while repairing |

Schema validation and hallucination bounds are engines, not agents. They run before a write is stored. A proposed fact that falls outside the neighborhood the conversation supports is dropped.

## Deterministic engines

Operating. They do not have a prompt.

- Methodology completeness, and the confirmation gate that closes a move once the founder has actually confirmed it
- Prerequisite structure as rows, distinct from the scaffolder that proposes them
- Leaf priority and influence scoring
- Normalization, success potential, and failure pressure
- Context assembly and harvest
- Post-save orchestration: propagate the preview, then start the background care

## Administration-only

| Role | Mandate | Forbidden |
| --- | --- | --- |
| Prompt curator | Help an operator revise an agent instruction against the prompt method | Run inside a founder session |

Model choice for background agents is an operator control. The founder sets whether selected background care is manual or automatic. Neither control lets a founder session rewrite another agent’s mandate.

## How a turn fits together

On a send, after the map is open:

1. Guardrail, when its cadence says so.
2. Coach reply, shown immediately.
3. Tier choice and harvest for the extractor.
4. Extractor draft in the background.
5. Local critic on that draft.
6. Preview updates to the verbatim commit set.
7. If the draft needs a clarification, a second coach message arrives without the founder having to ask.

Save propagates the preview and starts completeness, contradictions, estimates, and required moves. The founder is not held on the request while that finishes.

## Specified delivery roles

The next stage keeps this roster and adds roles whose subject is the founder’s own software, not only the plan. They are specified. They use the same rule: more narrow agents, not one agent with a mode switch.

| Role | Mandate | Forbidden |
| --- | --- | --- |
| Workflow orchestrator | Sequence the delivery states. Apply the founder’s autonomy settings. Call the compiler and the acceptance runner | Write product code by improvisation |
| Product owner | Journey, outcome, and business acceptance | Own the technical contract alone |
| Business analyst | Technical contract, parameters, errors, and how hard the coding is expected to be | Write the file contents in the first version of the loop |
| Graph architect | Structure that stays valid as the tree grows | Implement the feature |
| Delivery agent | Implementation sections on the units the contract names | Edit the accepted specification to fit the code |
| Graph critic | Verdict on a plan and on a proposal, during construction only | Write the graph. Enforce scope by itself |
| Background risk reviewer | Cyclic and on-demand risk across the plan | Sit inside the change batch as a rubber stamp |
| Incident analyst | Cross-layer account when a local fix loop has failed | Become the default implementer |
| Tester | Test intent and a verdict | Promote a release |
| Compiler | Materialize the graph into a tree, run the static gate, record the run | Act as an agent. Hold customer secrets in the graph |
| Acceptance runner | Test the promoted product, with secrets injected only into that run | Edit the tree. Put secrets into a prompt |

The proposer of a change cannot accept it. A critic’s agreement cannot waive a validator. That rule is the same one the factory already uses on itself.
